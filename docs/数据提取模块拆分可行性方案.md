# 数据提取模块拆分 · 可行性研究与实施方案

> 研究日期：2026-08-14　|　对象：`journal.py` / `journal_save.py` / `magazine.py`
> 实测存档：`tools/melt.json`（约 207 MB 熔化 JSON，巴西 1873 年，30 个玩家州）

## 一、结论（先说结果）

**可行，而且收益明确。** 但有两点与直觉不同，需要先说清楚：

1. **"拆到一个独立 .py"这件事其实已经基本完成了。** 所有检测/提取逻辑——熔化存档、POP、建筑、州、战争、战役、舰船、外交、法律——已经全部集中在 `journal_save.py`（约 266 KB）这一个文件里；`journal.py`（报纸渲染）和 `magazine.py`（杂志渲染）只是"消费者"，不直接碰存档。
2. **真正浪费性能的不是"没拆文件"，而是"同一份熔化 JSON 被反复整文件扫描"。** 实测一年生成的解析开销约 **52 秒**（快照提取 41.4s + 杂志数据 9.9s），其中 POP 相关遍历占了大部分；同一进程内多个函数各自独立重扫 `pops`、`country_manager` 等大区块。

所以方案的核心不是"再拆一个 .py"，而是**在数据层内做一次解析、多处复用，并把结果落盘缓存**，让报纸/杂志任何时刻都能"直接运行一次程序拿到数据"。

## 二、现状梳理

### 2.1 文件分工

| 文件 | 角色 | 与本次课题的关系 |
| --- | --- | --- |
| `journal_save.py` | **数据层**：熔化存档、提取快照、构建报纸/杂志数据 | 就是"检测模块"本体 |
| `journal.py` | 报纸渲染层：把 data dict 拼成提示词、调 DeepSeek | 消费者 |
| `magazine.py` | 杂志渲染层：基于 `data["magazine"]` 拼文章 | 消费者 |
| `style.py` | 文风/提示词模板 | 与数据提取无关 |

### 2.2 当前数据流（watch / continue 模式）

```text
检测到新存档
  → 熔化一次 (rakaly → tools/melt.json，约 207MB，仅此一次)
  → extract_full_snapshot(melted)          # 一次，约 41s
  → build_journal_data(snap)               # 纯组装，快
      → journal.on_block_complete          # 落盘 raw_<year>.json（报纸数据缓存）
  → build_magazine_data(melted, snap,...)  # 再扫一遍，约 10s
      → magazine.generate_magazine         # 落盘 magazine_<year>.json（完整杂志数据集）
```

### 2.3 已有的缓存

| 缓存文件 | 内容 | 现状 |
| --- | --- | --- |
| `tools/melt.json` | 熔化后的完整存档 JSON | watch 内一年只用一次；但单独跑 `newspaper <年>` / `magazine <年>` 会重新熔化 |
| `output/<玩家>/data/raw_<year>.json` | 报纸用 data dict | `journal.py regen` 已能完全靠它离线重生成报纸 |
| `output/<玩家>/data/magazine_<year>.json` | **完整的杂志数据集**（battles/migrations/promotions/士兵/平民/…） | 目前只作调试留存，重生成杂志时没有读取它 |
| `output/<玩家>/data/pops_<year>.json` | POP 跨年指纹 | 已用于跨年比对 |

### 2.4 重复遍历的实证

对 `extract_full_snapshot` 做 cProfile 剖析（巴西 1873）：

- `_iter_pops_in_states`（政治运动提取用）对**存档内全部约 31 万个 POP** 逐个做完整 `extract_json_object` + `json.loads`，再筛州；profile 中 `extract_json_object` 被调用约 31 万次，是最大热点（剖析累计约 64s / 40s 墙钟）。
- `_pops_by_state`、`_aggregate_pops` 已经用了"先读前 600 字节快速筛州、命中才完整解析"的优化（各约 3s / 7s 剖析），但**每次仍是从头扫一遍整个 pops.database**。
- `extract_full_snapshot` 与 `build_magazine_data` **各自独立调用 `_build_indexes`**，重复全扫 `country_manager` 与 `diplomatic_plays`。
- 一年内 pops.database 至少被整文件扫 4 次：`_aggregate_pops`（民族/宗教/职业占比）、`_pops_by_state`（采访样本）、`_iter_pops_in_states`（政治运动）、`_player_pops_with_id`（杂志样本与指纹）。

### 2.5 已存在的复用

- watch/continue 模式下，报纸和杂志**共享同一次熔化 + 同一个快照**（`_generate_async` 把 `snap`/`melted` 同时传给两者），这部分已经做对了。
- `journal.py regen` 直接读 `raw_<year>.json`，不重扫存档。

## 三、可行性评估

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| 把检测模块拆到独立 .py | ✅ 可行（且基本已完成） | `journal_save.py` 就是那个文件；再搬文件不产生性能收益，只改善组织 |
| 进程内"解析一次、多处复用" | ✅ 可行 | 顶层区块（pops/states/country_manager/…）做记忆化，或至少把玩家州 POP 解析成 `{state_id: [pop...]}` 共用 |
| 快照/杂志数据落盘缓存 | ✅ 可行，成本极低 | 实测 snapshot 约 30KB、杂志数据约 120KB，完全 JSON 可序列化，落盘/加载几乎零成本 |
| 重复生成走缓存 | ✅ 可行 | 报纸侧已有 regen 先例；杂志侧数据已完整落盘，只差一条读取路径 |

### 风险点

1. **记忆化上下文会改函数签名**：`extract_full_snapshot` / `build_magazine_data` 及内部几十个解析函数要改为接收共享上下文，涉及 `tools/run_test3.py`、`run_test4.py` 等调用点，改动面中等偏大，需要回归验证。
2. **不建议"整份 json.loads"**：207MB 熔化 JSON 转成 Python dict 约需 2–4GB 内存，晚局存档更大；用"区块级解析一次"或"头部快速筛州"更稳。
3. **缓存有效性**：快照缓存必须绑定存档（mtime/玩家），换档、换国、回滚存档时要能失效，否则会读到旧数据。
4. 各解析函数对存档结构的假设依赖具体版本（当前 1.13.x），重构时保持原有解析口径不变。

## 四、实施方案（分阶段，按"改动小、收益大"排序）

### 阶段 0：零风险小优化（推荐立即做）

把 `_iter_pops_in_states`（政治运动）改成与 `_pops_by_state` 相同的"前 600 字节快速筛州"技巧。

- 收益：政治运动提取从剖析约 40s 降到几秒，直接砍掉全年解析的最大热点。
- 改动：一个函数，无签名变化，无风险。

> ✅ **已于 2026-08-14 实施**：`_iter_pops_in_states` 已改为先读对象头 600 字节
> 快速筛州、命中才完整解析，不再对全部约 31 万个 POP 逐个 `json.loads`。

### 阶段 1：进程内共享"存档读取上下文"（SaveContext）

在数据层新增一个上下文类（可放 `journal_save.py`，或独立 `save_context.py`）：

- 持有 melted bytes；
- 惰性解析并**缓存一次**：玩家州 POP 索引 `{state_id: [pop对象]}`、国家索引 + 列强 + dp_index、建筑索引、states 数据库、pacts/treaties/characters 等；
- `extract_full_snapshot(ctx, cid)` 与 `build_magazine_data(ctx, snap, folder, year)` 改为共享同一个 ctx。

- 收益：新年份解析从约 52s 降到预计 25–35s（消除 POP 重复解析与 `_build_indexes` 重复全扫）。
- 改动：中等，需回归对比同一年数据是否一致。

> ✅ **已于 2026-08-14 实施**：在 `journal_save.py` 内新增 `SaveContext`（未拆新文件），
> `extract_full_snapshot` / `build_magazine_data` / `make_newspaper` / `make_magazine`
> 均接受 `ctx=None`，watch/continue 创建一次后共享给报纸与杂志：
> - 国家索引/列强/dp 只建一次（`ctx.index()`）；
> - 玩家州 POP 只扫描解析一次（`ctx.player_pops()`），占比统计、按州索引、
>   政治运动、杂志样本全部复用同一份 `{pid: pop对象}`；
> - 州对象按 id 惰性缓存（`ctx.state_object/state_region_key/state_zh`），
>   避免旧代码每查一个州就线性扫一遍 states 库；
> - 角色索引按 id 集合缓存、建筑索引与编成按需缓存。
> - 实测：共享 ctx 下 提取 41.4s → **18.4s**，杂志构建 9.9s → **4.5s**，
>   新年份全流程约 **23s**（原约 52s）。
> - 回归：用 git HEAD 旧代码在同一份 melt 上对比，除 POP 统计字段外
>   所有字段（战争/战役/外交/法律/采访样本/杂志全文案数据）完全一致。
>
> ⚠️ **附带的数据修正**：旧 `_aggregate_pops` / `_extract_player_states` 的头部扫描
> 用"第一个 `}` 跳位"，遇到含嵌套对象的 POP 会错位重复计数，导致巴西 1873 总人口
> 被算成 1.04 亿（存档官方口径约 2406 万）。重构后统一走严格边界解析，总人口约
> 2303 万、各族/宗教/职业占比随之修正（与杂志侧一直使用的 `_player_pops_with_id`
> 口径一致）。这是修 bug 而非回归，但**报纸中的民族/宗教/职业数字会变化**。

### 阶段 2：快照落盘缓存（推荐与阶段 0/1 并行）

- `extract_full_snapshot` 结果落盘为 `snapshot_<year>.json`（或并入 `raw_<year>.json`）；
- `newspaper <年>` / `magazine <年>` 先读缓存（校验存档 mtime/玩家），缓存命中就不再熔化、不再提取，直接走 `build_journal_data` / 渲染；
- `regen` 同样受益。

- 收益：同一年的第二次及以后生成（含换风格重生成、补生成）从约 52s 降到约 1s。
- 改动：小，纯增量。

> ✅ **已于 2026-08-14 实施完成**（未拆分新文件，改动全部在 `journal_save.py`）：
> - 新增 `_save_snapshot_cache` / `_load_snapshot_cache` / `_snapshot_cache_path`，缓存写为
>   `<journal_dir>/<folder>/data/snapshot_<year>.json`（实测约 32KB），内含 `_meta`
>   （存档文件名 + mtime + 年份 + 玩家 + 会话文件夹）用于校验。
> - `make_newspaper` / `make_magazine` 在未传入 `snap` 时优先读快照缓存；校验不通过
>   （换档/重存/换国）自动回退到熔化+提取，并重新落盘缓存。
> - 缓存只存 `extract_full_snapshot` 的纯提取结果，跨年补回的战争
>   （`_merge_prev_year_wars`）每次读取后重新合并，与历史行为一致。
> - 报纸缓存命中实测 **约 0s**（跳过约 41s 提取）；杂志缓存命中约 11s（仍需
>   `build_magazine_data` 约 10s，读取 melt 缓存约 0.5s，跳过约 41s 提取）。
> - 缓存读取只扫 `<journal_dir>/<folder>/data/` 一级深度，不会误取 `test*/` 测试目录。

### 阶段 3：杂志缓存直读（可选）

- 新增 `make_magazine_from_cache(year)`：加载 `raw_<year>.json` + `magazine_<year>.json`，直接调 `magazine.generate_magazine`。
- 收益：杂志单独重生成完全离线，连熔化缓存都不用读。

> 📊 **探索结论（2026-08-14）**：`magazine_<year>.json`（约 190KB）与
> `raw_<year>.json` 均已完整落盘，读取约几十毫秒；相比 `build_magazine_data`
> （新 ctx 下约 9.9s，共享 ctx 下约 4.5s）可再省约 5–10s。但杂志重生成主要耗时在
> DeepSeek 的十几次 API 调用（分钟级），省这 5–10s 对用户体验影响有限；
> 对调试/离线重渲染有意义，建议需要时再做。

### 阶段 4：区块级单次解析（远期可选）

- 每个顶层 manager 区块（country_manager / pops / states / building_manager / war_manager / battle_manager / …）各解析一次为 Python dict 并缓存，所有查询函数从缓存取。
- 收益最大（理论可把 52s 再降到约 10–20s），但改动面最大，应逐步替换并每步回归。

> 📊 **探索结论（2026-08-14）**：
> - "整份 json.loads"实测 207MB 熔化 JSON 需 **21.2s + 峰值约 1.4GB 内存**，
>   与当前整个提取流程（18.4s）几乎持平，且内存代价大，**不建议**。
> - 剩余热点（新代码剖析）：POP 单次扫描约 7s、laws 查询约 4.7s、国家索引约 3.9s、
>   家庭采访约 4.2s、建筑索引约 2.7s、玩家定位约 2.6s（剖析值，墙钟约为一半）。
> - 可选的"聚焦式"改进：laws 数据库按 ctx 缓存、玩家定位并入国家索引构建、
>   角色库一次解析供陆海战共用——预计可再省 3–5s（18.4s → 13–15s）。
>   完整 dict 化改写收益有限（受内存与改动面制约），当前阶段不建议。

## 五、验收与回归

1. **数据一致性**：改造前后，同一存档同一年的 snapshot / 杂志数据 JSON 应逐字段一致（随机采样已由 year 播种，天然确定）。
2. **耗时基准**（巴西 1873，207MB melt）：
   - 熔化缓存读取 0.55s；`extract_full_snapshot` 41.4s → **18.4s**；
     `build_magazine_data` 9.9s → **4.5s**（共享 ctx）/ 9.9s（独立 ctx）；
   - 新年份共享 ctx 全流程 **约 23s**；报纸快照缓存命中约 0s；
     杂志快照缓存命中约 10.5s（独立新 ctx）。
3. **命令级验证**：
   - `python journal_save.py newspaper 1866`（应命中缓存，秒级完成）
   - `python journal_save.py magazine 1866`
   - `python journal.py regen 1866`
4. 用 `output/` 现有年份做回归基准，输出目录中已有的 `raw_*` / `magazine_*` 文件可直接对比。

## 六、建议路线

- **已完成（2026-08-14）：阶段 0 + 阶段 1 + 阶段 2**，全部改动在 `journal_save.py`：
  新年份全流程约 52s → **23s**，报纸重复生成约 0s，杂志重复生成约 10.5s。
- **阶段 3**：收益约 5–10s/次但杂志重生成主要耗时在 LLM 调用，建议需要时再做
  （调试/离线重渲染有意义）。
- **阶段 4**：实测"整份 json.loads"需 21s + 1.4GB 内存，不划算；聚焦式缓存
  （laws/角色库/玩家定位）预计再省 3–5s，改动可控，可作后续可选优化。
- 文件层面：**建议保持 `journal_save.py` 作为数据层本体**，新增缓存/上下文类放在同文件或新建 `save_context.py`；不建议把几十个函数搬到新文件而只改变导入关系（纯搬家，无性能收益，反而增加回归成本）。
